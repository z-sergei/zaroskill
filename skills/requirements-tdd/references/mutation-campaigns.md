# Mutation checks within TDD

Use existing red–green evidence when it already demonstrates the relevant regression. Investigate a consequential uncertainty with a focused behavioral fault; choose a broader automated campaign for a rule set that warrants it or when explicitly requested. Discover the configured tool and its language/compiler/runner support. Keep new tooling integration a scoped choice, rather than a prerequisite for each slice.

Use a green baseline with the intended tests discovered. Limit target code, operators and run cost; keep requirements and assertions unchanged during measurement. An automatic operator set may miss domain mistakes, so include a focused workflow fault if that is the open question. Strengthen a test from the independent contract, then record a separate remeasurement.

For important survivors, find a permitted input and promised observation that distinguish the mutation. Classify missing protection separately from equivalent or unreachable changes. Inspect failures: domain exceptions may reveal a real regression; build/discovery failures do not establish meaningful sensitivity. A reported timeout needs a causal check when it supports the conclusion. Review cache validity after dependency or configuration changes and justify narrow exclusions; a numerical target does not justify weakening expectations or hiding mutants.

Finish with actual scope, results and remaining gaps. Stop at the scoped evidence or execution budget. Mutation score cannot establish omitted requirements or refactor resistance. When reducing tests, check that distinct contract obligations and relevant fault detections remain protected; a green baseline or the same finite kill set alone does not justify deletion.
