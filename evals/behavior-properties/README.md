# Сценарии, свойства и работоспособность проверок

Дата: 2026-10-24. Обновлены четыре личных навыка. Цель — связывать понятный сценарий с общим правилом, проверять достижимость и активность утверждения, различать решение компонента и результат для пользователя, а также отделять прогресс операции от времени жизни сервиса.

## Слепое сравнение первой редакции

Два агента со свежим контекстом получили одинаковые восемь заданий и разные изолированные версии навыков. Каждый выполнял все восемь заданий последовательно; это один парный прогон, а не восемь независимых экспериментов. Третий агент оценил анонимные ответы A/B, исходные задания и результаты механических проверок без доступа к соответствию версий. Оно раскрыто после итогового решения: **A — первая новая редакция, B — исходная версия** из коммита `8c401fd17ca30d41b261d6340a859e0d627ceadd`.

| Задание | Фактический результат обеих версий |
| --- | --- |
| C01 — реализовать кассу через TDD | Прошли 4 собственных и 3 независимых контрактных теста; в журнале 4 цикла red → green. |
| C02 — написать тесты поиска через реальный координатор | Обнаружены 4 из 4 заложенных ошибок; 2 из 2 допустимых рефакторингов сохранили зелёные тесты. |
| C03 — оценить условную проверку | Найдена недостижимая проверка: число состояний не подтверждает защиту от старого ответа. |
| C04 — оценить оптимизированный запуск | Найдены отключённые утверждения: в этом режиме Python удаляет bare `assert`. |
| C05 — здоровые проверки тарифа | Замечаний нет; целочисленный домен и активные проверки `unittest` учтены. |
| C06 — оценить бюджет опроса | Показан запрещённый четвёртый опрос: сброс бюджета разрушает предел операции. |
| C07 — оценить восстановление inbox | Допустимое ожидание и дедупликация оценены верно; обе версии пропустили недостаточную предпосылку завершения. |
| C08 — здоровые проверки отправки | Замечаний нет; соседний успешный сценарий и проверка внешнего порта учтены. |

Итог: **8 ничьих**, три целевых дефекта найдены обеими версиями, ложных замечаний на двух безоговорочно здоровых контролях C05/C08 нет. Сам по себе этот прогон не доказывает превосходство новых инструкций. Первая редакция сохранена как явное уточнение запрошенного подхода с проверкой отсутствия регрессий на этих задачах.

### Что оказалось неверно в оценочном стенде

C05 был одинаково уточнён до появления соответствующих отчётов: на этой границе входы уже проверены как целые числа. Сохранены [поправка](fixture-clarification.json) и хеши входов до и после неё.

В исходной рубрике C07 помечен здоровым без достаточных оснований. После первого решения судью попросили отдельно проверить, следуют ли выводы о прогрессе из задания. Он подтвердил общий пропуск: процесс может каждый раз прерываться после receipt, но до устойчивой записи Answered. Получение ответа и повторное планирование не исключают такой бесконечный цикл. Это недостаток заявленной гарантии, а не установленный баг реализации. [Окончательное решение судьи](judgment.md) сохраняет это ограничение; исходная рубрика оставлена как исторический артефакт.

## Узкое уточнение после сравнения

В `state-machine-verification` добавлено различие между возможностью повторить попытку и гарантией прогресса. Для завершения нужен явно поддержанный путь к устойчивому результату: например, конечное число прерываний и последующее выполнение записи. Этой инструкции ещё не было в слепо сравниваемой редакции.

Для проверки подготовлены четыре задания: неограниченные перезапуски между receipt и записью, ограниченные перезапуски с явным исполнением записи, допустимое ожидание человека и сбрасываемый бюджет опроса. Это отдельная направленная проверка, а не продолжение слепого сравнения.

Свежий агент с окончательной версией правильно разобрал все четыре: P01 — гарантия не следует, приведён бесконечный допустимый цикл; P02 — завершение следует из явных предпосылок, дедупликация сохраняется; P03 — дефекта нет; P04 — после третьего ответа возникает запрещённый четвёртый опрос. Он отделил аналитические выводы от неисполненных предложений тестов. [Оценка результата](progress-probe/assessment.json). Исходная версия на этих четырёх заданиях повторно не запускалась, поэтому причинный эффект одной формулировки не измерен.

## Артефакты и воспроизведение

- [Протокол](protocol.json), [исходная рубрика](rubric.json), [машинное решение судьи](judgment.json), [раскрытие версий](version-map.json).
- [Исходные навыки](baseline-skills.json), [первая редакция](candidate-skills.json), [окончательная редакция](final-skills.json): хеши файлов. Первая редакция отличается от окончательной только дополнительным абзацем о прерывании перед устойчивой записью в `temporal-checks.md`.
- [Исходные задания](cases), [ответы A](runs/A/work), [ответы B](runs/B/work), журналы и механические результаты сохранены. Абсолютные временные пути в исходных журналах описывают фактический запуск на машине автора.
- [Проверка эталонных fixtures](fixture-preflight.json) выполнена до оценивания ответов; механика в [grade.py](grade.py) использует стандартную библиотеку Python.
- [Дополнительное задание](progress-probe/task.md), [ответ](progress-probe/report.md), [хеш использованного навыка](progress-probe/skill-manifest.json) и [точная поправка после сравнения](progress-probe/change.patch).

Для повторного исполнения механических проверок скопируй этот каталог во временную папку и из неё выполни:

```sh
python3 -B grade.py preflight
python3 -B grade.py runs/A
python3 -B grade.py runs/B
```

Команды заново выполняют сохранённые тесты и перезаписывают машинные результаты в копии. Они не вызывают моделей и не восстанавливают самостоятельно историю red → green; журнал этой истории сохранён отдельно.

Все случаи теперь открыты и являются материалом разработки. Один прогон на версию, последующее уточнение C07 и направленный повтор не дают статистической оценки превосходства. Формальное доказательство и тесты реального приложения в этой кампании не запускались.
