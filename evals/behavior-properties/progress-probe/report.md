# Проверка P01–P04

Источник требований — `task.md`; применены локальный `skill/SKILL.md` и разделы `references/temporal-checks.md` о прогрессе, повторах и эффектах. Граница анализа — описанные переходы работника, получателя, киоска и сервиса. **Inspected:** условия и допустимые трассы разобраны аналитически. **Not executed:** код, тесты, перебор состояний и формальная модель не запускались. Аналитические аргументы ниже не являются результатом формального верификатора.

## P01 — eventual Done не следует из условий

**Предложенная гарантия:** каждый принятый документ когда-нибудь получит долговечный статус Done. Долговечный Pending, стабильный ID и повторная выдача квитанции обеспечивают восстановление попытки, но сами по себе не обеспечивают её завершение.

**Inspected — контрпример:** `Pending(id) → Send(id) → Receipt(id) в памяти → Restart → Pending(id) → …`. Повторять этот цикл можно бесконечно. Каждый Send получает ответ, работник планируется, а перезапуск всякий раз происходит между получением квитанции и долговечной записью Done. Все явно заданные предпосылки соблюдены; Done никогда не появляется. Это допустимая бесконечная трасса, а не вывод о прогрессе из конечного теста.

Не хватает условия, обеспечивающего завершение необходимого участка: например, конечного числа перезапусков и последующего исполнения записи либо иной явной гарантии, что запись Done когда-нибудь успеет выполниться. Дедупликация получателя сохраняет **не более одной фиксации на ID**, но не устраняет локальное голодание записи Done.

**Минимальное следующее свидетельство, not executed:** сценарий через реальную границу хранения — прервать работника после квитанции, восстановить Pending с тем же ID, получить исходную квитанцию повторно. Он проверит соответствие одного оборота цикла реализации; никакое конечное число таких оборотов не докажет eventual Done. Для этой гарантии нужно обосновать дополнительное условие прогресса.

## P02 — eventual Done следует при заданном дополнительном контракте

**Inspected — аргумент:** для каждого документа после не более двух перезапусков наступает суффикс исполнения без перезапусков; если их нет, он начинается сразу. В этом суффиксе Pending продолжает работу, Send получает квитанцию, а необходимые локальные шаги, включая долговечную запись, в итоге выполняются успешно. Следовательно, предложенная гарантия Done выполняется в рамках описанной системы.

Повторные отправки возможны, в том числе после уже совершённой фиксации у получателя. Однако стабильный ID, фиксация получателем не более одного раза на ID и возврат исходной квитанции исключают повторную фиксацию **того же ID**. Это не обещание единственной отправки или единственного ответа. Условие не задаёт срок в секундах: eventual Done не даёт временного дедлайна. Вывод не распространяется на эффекты вне указанного контракта получателя.

**Минимальное следующее свидетельство, not executed:** два перезапуска после получения квитанции, но до записи Done, затем успешное продолжение. Проверить долговечный Done, сохранение ID и одну фиксацию у получателя. Такой сценарий проверяет опасную границу восстановления; универсальный вывод дополнительно опирается на заданное ограничение перезапусков и успешное исполнение шагов после последнего из них.

## P03 — отсутствие общего завершения не является дефектом

**Inspected:** бесконечное ожидание в активном preview допустимо: действие человека необязательно, срока ожидания нет. Приложение по условию продолжает обслуживать будущих пользователей, поэтому требование завершения всего приложения отсутствует.

Положительное обязательство относится к конкретному действию: `PreviewActive → Leave → PreviewClosed`. По условиям Leave закрывает preview сериализованным локальным переходом. Необходимость завершить этот переход не превращает ожидание человека или жизнь приложения в операции с обязательным завершением. Оснований добавлять таймаут или объявлять ожидание зависанием нет.

**Минимальное следующее свидетельство, not executed:** сценарий через настоящий обработчик Leave: preview закрывается, приложение остаётся доступным следующему пользователю. Наблюдение некоторого периода бездействия само по себе не доказывает корректность бесконечного ожидания; его допустимость здесь следует из требований.

## P04 — нарушена граница одного Check

**Требование:** один Check завершается Ready либо StillPending не позднее третьего ответа опроса; только новый явный Check начинает новый бюджет. Долгая жизнь фонового сервиса этому не противоречит.

**Inspected — конечный контрпример:** начать один Check; получить три последовательных Pending с предложением сервера `3`. После каждого ответа обработчик делает `remaining := 3; remaining := remaining − 1`, поэтому значение каждый раз равно `2`. После третьего ответа Check всё ещё не завершён и запускается четвёртый опрос — обещание уже нарушено. Если ответы Pending продолжаются, получается бесконечный Check, хотя каждый запланированный опрос возвращает ответ. Новый явный Check для этой трассы не нужен.

Не хватает невосполняемого бюджета, принадлежащего одному Check: ответы должны расходовать оставшийся лимит, а третье Pending должно завершать Check как StillPending. Значение от сервера не должно увеличивать этот лимит. Это необходимое направление исправления, а не изменение исходного требования.

**Минимальное следующее свидетельство, not executed:** контролируемо вернуть три Pending с предложением `3` через реальный обработчик, проверить StillPending после третьего ответа и отсутствие четвёртого опроса. Затем новый явный Check должен получить новый бюджет. Наблюдать нужно и результат операции, и команды опроса; продолжающаяся работа самого сервиса не является нарушением.
