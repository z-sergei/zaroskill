# C07 — анализ без исполнения

Статус: inspected. Источники: task.md, разделы temporal-checks.md о прогрессе, retry и внешнем эффекте. Реализация не запрошена и не предоставлена; тесты, симуляция и формальная модель не запускались. Ни один выполненный тест или формальное доказательство не заявляется. Кратких трасс и заданных допущений достаточно для этого анализа.

Обязательства из task.md: service остаётся жив для будущих ticket. Каждый ticket имеет отдельного владельца/состояние; Assigned может неограниченно ждать добровольного ответа клиента, без гарантии истечения. После submit ответа worker должен доставить сообщение и записать Answered. Предполагаются eventual scheduling worker и eventual acceptance повторяемого запроса endpoint; все заявленные предпосылки выполняются. Durable pending и message ID переживают перезапуск.

Безопасность: повторные send одного durable ID могут выполняться много раз, но endpoint фиксирует ID лишь однажды и возвращает прежний receipt. Cancel и submit сериализованы: cancel первым -> Cancelled без send; submit первым -> отправка началась, поздний cancel не меняет её на успешную отмену. Ответы разных ticket не разделяют владельца pending.

Различающие трассы (аналитические, не исполненные):

1. Queued -> Assigned -> отсутствие добровольного ответа бесконечно. Разрешённое ожидание; нет нарушенной обязанности завершить этот ticket.
2. Assigned -> Cancel -> Cancelled -> попытка submit не отправляет сообщение. Это заданная политика сериализации.
3. Assigned -> submit -> durable pending(ID=m) -> send(m) -> endpoint commit(m, receipt=r) -> interruption до записи Answered -> supervisor restart из pending(m) -> повтор send(m) -> тот же receipt r -> Answered. Число запросов может быть >1, число commit(m)=1.
4. Assigned -> submit -> поздний Cancel сообщает «отправка уже началась»; worker продолжает получать receipt и отмечает Answered. Нельзя одновременно заявить успешную отмену и разрешить committed отправку.

Прогресс после submit: pending сохраняется до receipt, retries не прекращаются преждевременно, endpoint в итоге принимает запрос и повторно выдаёт тот же receipt; worker получает возможность выполнить обработку и запись Answered по заданным предпосылкам. Перезапуск продолжает то же логическое сообщение. Эта обязанность относится к per-ticket worker после submit, не ко всему сервису и не к периоду ожидания необязательного ответа. Нет основания требовать deadline, конечного числа попыток или завершения процесса.

Полезные проверки будущей реализации: контролируемый endpoint с учётом commit по ID; interruption до/после удалённого commit и перед локальным Answered; retry с прежним ID, commit ровно один и eventual Answered. Два порядка сериализованных Cancel/submit: отсутствие send при Cancel первым и корректный ответ на поздний Cancel. Эти проверки предложены, а не выполнены; недостаток такой реализации по одному описанию не заявляется.
