Подтверждённой проблемы в описанном дизайне нет при всех данных предпосылках. Постоянная работа сервиса нужна для будущих обращений. Отдельный Assigned-ticket вправе неограниченно ждать необязательного ответа клиента; требование завершить каждый такой ticket или весь процесс отсутствует.

Безопасность отправки обеспечивается на уровне внешнего commit: повторные запросы с одним durable message ID могут быть многочисленными, но endpoint фиксирует сообщение один раз и возвращает одинаковый receipt. При прерывании после удалённого commit, но до локального Answered, supervisor восстанавливает pending с тем же ID; retry получает прежний receipt, затем worker записывает Answered без повторного эффекта. Это аналитическая трасса, а не выполненный эксперимент.

Сериализация разрешает конфликт Cancel/submit: Cancel до submit предотвращает отправку; submit первым делает позднюю отмену сообщением об уже начавшейся отправке. Противоречивое обещание «отменено, но отправлено» в описании отсутствует.

Прогресс обязателен после submit. При заданных eventual acceptance endpoint и eventual scheduling worker повторы приводят к receipt и Answered; durable pending позволяет продолжать после перезапуска. Не обещаны конечный срок по часам, ограниченное число retries или завершение сервиса. Бесконечное ожидание добровольного ответа до submit не является контрпримером этой гарантии.

Область — анализ дизайна; кода для проверки нет. Исполнение и формальная модель не нужны и не выполнялись. Полезные проверки будущей реализации: восстановление вокруг удалённого commit/локальной записи, сохранение ID, один commit и последующий Answered, а также оба сериализованных порядка Cancel/submit. Описанные механизмы не следует считать проверенными в реальном коде без этих свидетельств. Подробности — evidence.md.
