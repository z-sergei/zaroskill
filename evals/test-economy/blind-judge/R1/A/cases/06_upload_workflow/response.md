# Результат и контракт

Изменён только `test_upload.py`: три исходных сценария усилены, четыре добавлены. `upload.py` сохранён. Все обещания взяты из `task.md`, а не выведены из приватных полей реализации.

Граница проверки — одна реальная `UploadSession`, последовательные вызовы публичных методов, наблюдаемые `state`, `result` и возвращаемые значения. Новая сессия создаётся обычным конструктором; остальные состояния достигаются через `begin`, `complete` и `cancel`. Тесты не читают и не устанавливают `_active_attempt` и `_last_attempt`.

Проверяемое safety-свойство: результат может принять только ожидающая сессия с активным id; чужие, старые и повторные завершения, а также отклонённый `begin`, не должны портить состояние и текущую попытку. После успеха или отмены разрешён новый `begin` с большим целочисленным id и очищенным результатом. Положительное обязательство проверяется завершением правильной попытки после отклонённых событий: реализация, отвергающая все завершения, тесты не пройдёт. Eventual delivery, потокобезопасность, таймеры и сеть вне контракта; ожидание без вызова `complete` разрешено.

## Различающие последовательности

Здесь A и B — id, фактически возвращённые этой сессией; их конкретные значения не зафиксированы.

| Сценарий | Значимый порядок и наблюдение |
| --- | --- |
| `test_success_survives_duplicate_completion_and_cancel` | `begin A → complete A → complete A с другим значением → cancel`. Успех принимается один раз; повторный результат и отмена не изменяют `done` и исходное имя файла |
| `test_cancel_rejects_late_completion_and_repeated_cancel` | `begin A → cancel → complete A → cancel`. Поздний callback после отмены остаётся отклонённым, результат `None`, повторная отмена возвращает False |
| `test_unknown_completion_preserves_current_attempt` | `begin A → complete чужого id → complete A`. Проверены отрицательный, нулевой и будущий неизвестный целочисленный id; каждый отклонён, а A всё ещё принимается |
| `test_events_while_idle_do_not_prevent_a_later_upload` | `cancel → complete без begin → begin A → complete A`. Пустая сессия сохраняется после лишних событий и остаётся пригодна для работы |
| `test_rejected_begin_preserves_the_active_attempt` | `begin A → begin с RuntimeError → complete A`. После ошибки немедленно проверяются `waiting/None`, а сохранение активной попытки подтверждается принятием A |
| `test_restart_after_success_clears_result_and_rejects_old_completion` | `begin A → complete A → begin B → complete A → complete B`. B больше A, старое имя очищено сразу при старте B, запоздавший A не занимает место B |
| `test_restart_after_cancel_rejects_old_completion_and_accepts_new_attempt` | `begin A → cancel → begin B → complete A → complete B`. Повтор после отмены получает новый id, прежний callback не принимается и не лишает B права завершиться |

После каждого значимого события проверяется состояние и результат до следующего события: финальный правильный результат не сможет скрыть временную запись устаревшего значения. Для callback используются разные имена файлов, чтобы ошибочная перезапись была видна. Возвращаемые `True`/`False` проверяются как конкретные boolean-значения. Активность попытки проверяется через следующий публичный `complete`, без привязки к внутреннему устройству класса.

Две стороны порядка «успех/отмена» имеют разные последствия, поэтому сохранены оба сценария. Повторный старт из `done` должен очистить существующий результат; старт из `cancelled` должен восстановить рабочую сессию после другого терминального состояния. Их одинаковое конечное `done` не делает истории взаимозаменяемыми. Чужой id внутри текущей попытки и старый ранее действовавший id проверяют разные происхождения неверного callback.

Выбраны семь коротких конкретных трасс, максимум пять вызовов методов и две успешно начатые попытки на трассу. Они покрывают указанные порядки, стороны отмены/завершения, повторное использование и отклонение событий, сохраняя локальную диагностику. Это не исчерпывающий перебор всех историй, не bounded model checking и не доказательство для произвольного числа перезапусков. Отдельный генератор состояний и формальная модель не добавляют необходимого свидетельства для этих локальных различий и увеличили бы сопровождение. Код ожиданий не копирует реализацию автомата.

## Реальные проверки

Команда в папке задания: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -v`.

- До изменений — 3 теста, `OK`, exit 0.
- После усиления — 7 тестов, `OK`, exit 0.
- Два узких fault-probe в `probes/06_upload`, каждый от оригинального production; исходные 3 теста проходили оба дефекта.
  - Сброс счётчика перед перезапуском из `done`/`cancelled`: усиленный набор дал 2 failures в сценариях повторного старта, `1 not greater than 1`.
  - Потеря активного id перед `RuntimeError` повторного `begin`: усиленный набор дал 1 failure, исходная попытка больше не принимается (`False is not true`).
- После восстановления копии и проверки неизменного SHA-256 настоящего `upload.py`: 7 тестов, `OK`, exit 0.
- После уточнения проверок truthiness до точных `True`/`False`: финальные 7 тестов, `OK`, exit 0. Fault-probe выполнены до этого уточнения; их наблюдения и числовые проверки не ослаблялись.

Полные контрольные и fault-выводы сохранены в `probes/06_upload/*.txt`; этапы — в корневом `execution.md`. Это исполненные сценарии и чувствительность к двум конкретным дефектам, а не историческое TDD исправление production или полная mutation campaign. Тесты и наблюдения охватывают только локальный жизненный цикл: вызов `complete` моделирует уже поступившее событие, а не доказывает выполнение или доставку реальной загрузки.
