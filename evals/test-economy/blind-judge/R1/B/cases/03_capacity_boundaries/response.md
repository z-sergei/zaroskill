# Ревью тестов резервирования

Вердикт: исходный набор полезен, но имел конкретный пробел при успешном запросе ниже лимита. Объединять пары domain/request только из-за похожих аргументов не стоит. По просьбе задачи внесены небольшие исправления тестов; production сохранён. Проверены все файлы этого самостоятельного проекта; иных локальных наборов или потребителей нет.

Карта контракта из task.md:

| Требование / вход | Наблюдение и защита |
| --- | --- |
| reserve(7, 3, 10), ровно лимит | возвращает 10; test_domain_allows_exact_capacity защищает включительность |
| reserve(7, 4, 10), превышение на один | CapacityError; test_domain_rejects_over_capacity теперь также проверяет обещанную совместимость с ValueError |
| reserve(10, 0, 10), заполнено | возвращает 10; отдельное разрешение нулевого запроса |
| reserve(2, 3, 10), есть запас | возвращает 5; добавлена проверка, отличающая сложение от возврата limit, requested или used |
| handle_request для тех же ситуаций | полный словарь status/used, отсутствие дополнительных публичных полей и неизменность payload; ошибки преобразуются в full с исходной занятостью |

Одинаковые входы на разных границах не дают одинакового диагностического сигнала. Прямые тесты reserve фиксируют поддерживаемый числовой результат и исключение. Тесты handle_request проверяют реальную связку с reserve, перевод исключения в full, точную схему ответа и входной словарь. Ошибка только в переводе ответа оставит domain-тесты зелёными; ошибка в арифметике затронет обе группы. Прямые проверки останутся полезными, даже если реализация обработчика позже перестанет вызывать reserve. Ровно лимит, превышение и ноль при полном заполнении — разные правила. Схожие несколько строк Arrange/Assert дешевле общей условной таблицы, которая смешивает возвраты и исключения; оправданного дублирования поведения для удаления не найдено.

Оценка четырёх измерений:
- Regression protection — исходно mixed: границы и обработчик проверены хорошо, но все успешные ожидаемые значения равнялись limit. После изменения strong в рассмотренных различиях: обычная занятость 5 явно отлична от 10. Это не доказательство всех целочисленных входов.
- Refactor resistance — strong по коду тестов: только публичные результаты, публичный тип исключения и входное состояние, без частных методов/моков. Отдельный refactor probe не выполнялся.
- Feedback/reliability — strong локально: детерминированный in-process unittest, 8 методов прошли, время, сообщённое runner, 0.000 s; процессный запуск имеет дополнительную стоимость, CI не измерялся. Пропусков и expected failures нет.
- Maintainability — strong: короткие независимые сценарии с буквальными значениями; имя каждого теста соответствует проверенному исходу. Переименован zero-at-capacity request-тест, поскольку теперь он также проверяет неизменность входа.

Находки по приоритету:
1. Medium, executed: прежние success-тесты в обеих группах не различали новую занятость и limit. В копии замена `return updated` на `return limit` оставила все 6 исходных тестов зелёными, хотя reserve(2, 3, 10) обязан вернуть 5. Минимальное исправление — по одному примеру на обе публичные точки входа; выполнено. Новые тесты дают две содержательные ошибки assert (10 != 5 и неверный used в словаре).
2. Low, demonstrated by code: прежний тест отказа проверял CapacityError, но не его обещанную принадлежность ValueError. Добавлено одно assertIsInstance пойманного исключения; отдельный fault probe для иерархии исключений не проводился.
3. Low, demonstrated by code: прежний request-тест нулевого запроса не сохранял ссылку на payload и не наблюдал его неизменность. Добавлен явный payload и одно сравнение; это дешёвая проверка особого допустимого пути. Прежние assertions для обычного успеха/отказа сохранялись.

Лучший следующий шаг уже выполнен: запрос 2 + 3 при limit 10, ожидаемые 5 и {status: ok, used: 5}. Новые тесты не рассчитаны на вне-контрактные значения.

Фактические проверки: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -v` в исходном случае: 6 тестов OK. Та же команда в probes/03_capacity_boundaries с возвратом limit: исходные 6 OK, дополненные 8 — FAILED (failures=2). После восстановления production в копии 8 OK; финально в исходной папке 8 OK.
