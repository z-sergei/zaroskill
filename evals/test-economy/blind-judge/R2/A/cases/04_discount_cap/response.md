# Ограничение скидки через TDD

Ведущий навык — `requirements-tdd`; источник ожиданий — `task.md`. Граница — публичная чистая функция `discounted_total`, существующий unittest без зависимостей.

План различающих примеров до реализации:

| Требование | Вход и ожидаемое наблюдение | Статус |
| --- | --- | --- |
| Лимит ограничивает скидку, а не итог | 1000 центов, 30%, лимит 200 → 800 | `test_cap_limits_discount_not_total`, red → green |
| Отрицательный лимит всегда запрещён | -1 при положительной и нулевой вычисленной скидке → ValueError | `test_negative_cap_is_rejected_even_when_computed_discount_is_zero`, red → green |
| Нулевой лимит допустим | 1000, 15%, лимит 0 → 1000 | `test_zero_cap_prevents_any_discount`, сразу green |
| Большой лимит не увеличивает скидку; округление сохраняется | 999, 15%, лимит 150 → 850 | `test_nonbinding_cap_preserves_rounded_percentage_discount`, сразу green |
| Явный None сохраняет старое поведение | 999, 15%, None → 850 | `test_explicit_none_preserves_uncapped_discount`, сразу green |
| Новый аргумент только именованный | Третий позиционный аргумент → TypeError | `test_discount_cap_must_be_passed_by_keyword`, сразу green |
| Старые вызовы и валидация | Шесть исходных тестов | База: 6 тестов OK |

## Наблюдаемая последовательность

Все команды — `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest ...` из папки задания; `python` отсутствует в окружении. Полные команды и выводы сохранены в корневом `execution.md`.

1. До изменений `discover -v`: 6 тестов, OK, exit 0.
2. Сначала добавлен только тест связывающего лимита. `-v test_discounts.DiscountTests.test_cap_limits_discount_not_total`: 1 error, exit 1 — старый API не принимал `max_discount_cents` (`TypeError`).
3. Добавлено только объявление необязательного keyword-only параметра, без его обработки. Тот же тест: 1 failure, exit 1, `700 != 800`. Так наблюдалось именно отсутствие нужного вычисления после устранения препятствия API.
4. Скидка ограничена через `min(discount, max_discount_cents)` при значении, отличном от None. Тот же тест: OK; общий набор: 7 тестов, OK.
5. Затем добавлен тест отрицательного лимита. Отдельный запуск этого теста: 3 subTest failures, exit 1, `ValueError not raised` для `(1000,15)`, `(1000,0)`, `(0,15)` и лимита -1. Два последних примера проверяют разные причины нулевой скидки.
6. Добавлена безусловная относительно суммы/процента проверка отрицательного лимита. Тот же тест: OK; общий набор: 8 тестов, OK.
7. Дополнительные четыре проверки уже поддерживаемых последствий правила добавлены без изменения production. Финальный `discover -v`: 12 тестов, OK, exit 0. Эти случаи сразу зелёные; не называю их отдельными циклами TDD.

Шесть исходных тестов сохранены без ослабления: они уже различают 0%, обычный процент, округление вниз, 100% и недопустимые исходные аргументы. Новый связывающий пример отличает ограничение скидки от ограничения итоговой суммы; несвязывающий — от безусловного вычитания лимита; нулевой — от ошибочной проверки truthiness; None — от неверной обработки отсутствия ограничения. Позиционный вызов проверяет явно обещанную форму API. Не добавлялись все сочетания старых и новых входов: они повторяли бы уже доказанные различия без самостоятельного риска.

Итог: изменены только сигнатура, проверка нового ограничения и выбор меньшей скидки; целочисленная арифметика и прежние требования сохранены. Новая архитектура, моки, зависимости и отдельный рефакторинг не нужны. Проверена именно чистая функция; интеграционные обещания за пределами задания не делаются.
