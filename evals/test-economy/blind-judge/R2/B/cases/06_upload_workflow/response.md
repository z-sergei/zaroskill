# Временной контракт UploadSession

Источник требований — task.md. Граница — последовательные вызовы публичных
методов и наблюдения state/result. Production не изменён. Обязательное свойство:
результат принимает только ожидающая его активная попытка; отказ не должен менять
состояние, результат или владельца ожидания. Положительное обязательство проверено
успешным complete текущего id, в том числе после отклонённых событий.

Семь именованных тестов различают следующие истории:

- idle → чужой complete → cancel → begin → правильный complete: события до старта
  ничего не меняют и не мешают реальной загрузке.
- begin → complete → повторный complete → cancel → чужой complete: принятый
  результат не перезаписывается. Это порядок, противоположный отмене до результата.
- begin → cancel → поздний complete → повторный cancel: отмена окончательна для
  этой попытки; поздний callback не оживляет её.
- begin → чужие id по обе стороны активного → правильный complete: проверяются
  не только видимые значения, но и сохранение активной попытки через её успех.
- begin A → запрещённый begin → complete A: RuntimeError не теряет владельца.
- Для обоих префиксов (A завершилась / A отменена): begin B → complete A →
  complete B → complete A. Старый результат отвергается как до, так и после
  результата B; новый запуск сбрасывает прежний результат.
- Успешная A → отменённая B → begin C → результаты A и B → результат C:
  история содержит две разные устаревшие попытки и три возрастающих id. Пустая
  строка также сохраняется как допустимый результат.

После каждого существенного события проверяется снимок state/result и точное
булево возвращаемое значение. Каждый успешный begin проверяется на тип int,
положительность и рост относительно предыдущего; шаг ровно на единицу не
предполагается. Подтесты подписаны состоянием предшествующей попытки или id,
поэтому сбой показывает различающую историю. Приватные поля не используются.

Это небольшой набор конкретных трасс, а не перебор всех историй. Он защищает от
потери корреляции, повторного принятия, перезаписи результата, сброса счётчика и
потери владельца при отказе. Третий запуск добавляет отличимую историю, которую
одна пара id не проверяет. Дальнейшие одинаковые циклы увеличивали бы поддержку
без нового выделенного риска. Полнота для произвольной длины истории, потоки,
таймеры, I/O и гарантия eventual completion здесь не заявляются.

Выполнено `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -v`:
исходно 3 теста, после изменения 7 тестов, оба запуска OK (exit 0).
В отдельной копии `probes/06_rejected_begin_loses_owner` внесена одна ошибка:
begin в waiting теряет активную попытку перед RuntimeError. Новый тест
`test_rejected_begin_preserves_current_attempt` реально упал на последующем
complete A (False вместо True, exit 1). Это проверка чувствительности свойства,
не мутационная кампания и не изменение production. Точный вывод — в общем
execution.md и probes/06_rejected_begin_loses_owner/result.txt.
