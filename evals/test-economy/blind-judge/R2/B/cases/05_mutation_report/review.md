# Ревью комиссии за отмену

Вердикт: тесты полезны, но пропускают существенное отличие на 47 часах.
Production соответствует контракту task.md; менять его по этому отчёту оснований
нет. Проверены все cancellation.py, test_cancellation.py и четыре записи JSON.
Результаты в mutation-report.json — **предоставленная синтетическая фикстура**,
а не исполненная здесь мутационная кампания. Ниже отдельно указаны мои локальные
проверки. Production, тесты и JSON остались неизменны.

## Существующая защита

| Требование | Реальное свидетельство / пробел |
| --- | --- |
| До 24 часов — половина | (0,100) → 50; (12,101) → 50 защищает округление вниз |
| 24–47 часов — четверть | (24,100) → 25; нет 47 часов и остатка при делении на 4 |
| С 48 часов — бесплатно | (48,100) → 0 и (72,100) → 0: граница и более ранняя отмена |
| Отрицательные аргументы запрещены | Каждый аргумент по отдельности вызывает ValueError |
| Неограниченные целые | Код использует точную целочисленную арифметику; тестов больших чисел нет |

Все 6 методов действительно обнаружены и выполнены, пропусков нет.

| Измерение | Оценка | Основание |
| --- | --- | --- |
| Защита от регрессий | mixed | Есть обе точные границы и нечётная половина, но сдвиг бесплатного порога на час раньше проходит |
| Устойчивость к рефакторингу | strong | Проверяется публичный результат/исключение, без приватных деталей и моков |

| Поддерживаемость | strong | Короткие тесты, видимые независимые ожидаемые значения, осмысленные имена и подписанные отрицательные примеры |

## Разбор каждой записи

**M1, SURVIVED — эквивалентное изменение, пробел не установлен.** Для любого
неотрицательного целого p существуют q,r: p = 4q+r, 0 ≤ r < 4. Тогда p//4 = q
и (p-p%4)//4 = q. Это аргумент для неограниченного контрактного домена, а не
вывод из шести примеров. Проверка отрицательных аргументов не меняется; другие
типы вне контракта. Не нужно добавлять тест, различающий эквивалентные реализации,
или считать эту запись плохой защитой. Оправданно пометить её equivalent в анализе
отчёта. Дополнительный запуск неизменных тестов на копии подтвердил бы лишь
совместимость с существующими примерами; математическая эквивалентность уже
установлена по коду. Такой запуск M1 здесь **не выполнялся**.

**M2, SURVIVED — реальный пропуск входной границы, средняя важность.** При
(47,100) контракт требует 25, замена возвращает 0: клиенту ошибочно предоставляют
бесплатную отмену. В test_cancellation.py есть 24,48,72, но нет 47; утверждения
на результат достаточны, отсутствует различающий вход. Минимальное действие —
добавить (47,100) → 25 или (47,101) → 25, который заодно различит округление
четверти. **Выполнено:** точная замена в probes/05_M2 прошла те же 6 тестов
(exit 0); отдельный вызов на (47,100) дал 0 вместо 25. Сильный дополнительный
контроль после будущего добавления — исходный код зелёный, M2 падает на этой
новой проверке. Он здесь **не выполнялся**, поскольку набор по заданию не меняется.

**M3, ERROR — ошибка инструментария в фикстуре, не свидетельство качества
утверждений.** Ноль тестов и ошибка импорта до discovery означают, что фикстура
не проверила мутацию. При этом test_half_fee_rounds_down уже различает её:
(12,101) должно дать 50, замена даёт 51. Добавление дубликата не оправданно.
Действие для настоящей кампании — исправить запуск worker и повторить эту запись;
зависимость здесь не устанавливалась. **Выполнено:** в probes/05_M3 неизменные
6 тестов обнаружены; именно test_half_fee_rounds_down упал с 51 != 50 (exit 1).
Это локальная чувствительность имеющегося теста, а не исправленный статус
предоставленного отчёта.

**M4, TIMEOUT — запуск не дошёл до тестов; причина не в продуктовой петле.**
Указан timeout handshake, tests_run=0, test-start не было. Сам код — конечная
арифметическая функция. По фикстуре нельзя объявить мутацию убитой, живой или
тесты медленными. test_at_day_boundary уже различает (24,100): контракт 25,
замена 50. Следующий шаг в реальной кампании — проверить worker startup и
повторить эту запись; повышать общий timeout тестов без диагностики незачем.
**Выполнено:** probes/05_M4 обнаружил те же 6 тестов; test_at_day_boundary упал
с 50 != 25 (exit 1), без timeout. Это подтверждает защиту от конкретного сдвига,
но не диагностирует несуществующий здесь внешний worker.

## Приоритет и стоимость следующего изменения

Первое полезное улучшение — один понятный пример (47,101) → 25. Помимо M2,
по коду существующих тестов он закроет не проверенное округление четверти:
ошибка `(paid_cents + 3) // 4` проходит текущий единственный четвертной пример
с 100, но на 101 вернёт 26. Это **статический вывод**, отдельная мутация
округления здесь не исполнялась. Пример (23,100) → 50 отдельно различил бы
другую сторону границы суток (`>=23` вместо `>=24`); он также только предложен.
Эти два коротких примера дают конкретную дополнительную защиту без фреймворка.
Отсутствие верхней границы чисел остаётся вне выполненного покрытия; точность
огромных значений не следует из отчёта. Не предлагаю расширять набор ради счёта
мутаций. Удалять существующие тесты по пересечению покрытия тоже не предлагаю:
48 и 72 различают граничный и обычный бесплатный сценарий.

## Исполненные проверки и ограничения

Команда baseline и каждого из трёх адресных опытов:
`PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -v`.
Baseline: 6 тестов, OK, exit 0. M2: 6, OK, exit 0. M3 и M4: по 6 тестов,
по одному содержательному assertion failure, exit 1. Каждый опыт содержит
ровно одну указанную замену и неизменные тесты. Прямые контрактные свидетели
исполнены отдельно от измеряемого набора. Хеши исходных четырёх файлов до/после
совпали. Полные выводы: execution.md и probes/05_M2/result.txt,
probes/05_M3/result.txt, probes/05_M4/result.txt в общей разрешённой папке.
Мутационный инструмент, установка зависимостей и внешняя кампания не запускались.
Процент качества из этих разнородных записей не вычисляется.
