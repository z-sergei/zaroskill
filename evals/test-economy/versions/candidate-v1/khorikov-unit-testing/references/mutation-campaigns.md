# Choose and interpret mutation evidence

Start with the question the run must settle. An observed regression failure or a focused behavioral fault may already establish the needed sensitivity. A broader campaign earns its cost for a consequential rule set, uncertain existing coverage or an explicit mutation task. Discover the repository's existing tool, supported language/compiler and test runner before choosing integration work; prefer its configuration and a bounded set of changed or important code. Separate a proposal to install new tooling from an already executable check.

Establish a green, meaningfully discovered baseline in the same configuration. Fix or report unrelated runner problems before interpreting mutations. State the target files, relevant fault operators, execution budget and exclusions. Keep submitted assertions and requirements stable during measurement. Record newly strengthened tests separately, then measure them again. Retain representative domain faults when automatic operators miss workflow mistakes such as accepting another operation's result.

Inspect significant survivors for a permitted distinguishing input and observable contractual difference. Separate a real missed fault, an unexercised path, an equivalent or unreachable mutation, and an inconclusive result. An unexpected domain exception may expose a real violation; a compile error, broken discovery or runner crash does not establish assertion quality. A timeout may detect genuine nontermination or reflect unstable infrastructure; investigate its cause when it affects the claim. Tool status and aggregate score alone are insufficient.

Reuse cached results only within the tool's validity assumptions, accounting for changed dependencies and configuration. Keep exclusions narrow and justified. Stop when the scoped question is resolved or the budget is reached; report remaining uncertainty rather than increasing tests or exclusions to chase 100%.

Mutation sensitivity does not establish correct requirements, omitted business behavior or resistance to refactoring. Check a suspected refactor coupling separately with a contract-preserving change. An equal kill set on this finite campaign is not sufficient reason to delete a test: inspect its business distinction, boundary, diagnostic value and historical purpose. After a proposed reduction, compare the affected contract evidence and relevant fault detections, not just a green ordinary run. Preserve the original source and report the campaign's exact scope and limits.
