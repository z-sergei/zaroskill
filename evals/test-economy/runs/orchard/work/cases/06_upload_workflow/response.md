# Проверка жизненного цикла UploadSession

Ведущий навык: `state-machine-verification`. Источник всех ожиданий — публичный контракт из `task.md`; граница проверки — последовательные вызовы методов одной сессии и публичные `state`/`result`. Потоки, доставка I/O и сроки завершения вне контракта. Production не изменялся.

Обязательные свойства: завершить ожидание может только текущая попытка; после отмены или завершения поздние события сохраняют наблюдаемый результат; новый запуск очищает результат и выдаёт возрастающий положительный целочисленный id. Также проверяется положительное обязательство: после отклонённого события правильное завершение по-прежнему принимается. Скрытая активная попытка наблюдается через такое завершение, без обращения к приватным полям.

В `test_upload.py` сохранены простые сценарии успешной загрузки и чужого id, усилена отмена и добавлены следующие различающие порядки:

- `begin(A) → cancel → complete(A)` и повторный `cancel`: отменённая попытка не оживает.
- `begin(A) → complete(A) → cancel → complete(A/чужой id)`: успешный результат сохраняется, дубликат с другим значением его не заменяет.
- `idle → complete → cancel → begin → complete`: отклонение событий вне ожидания не блокирует последующую работу.
- `begin(A) → begin(ошибка) → complete(A)`: исключение не теряет активную попытку.
- `begin(A) → complete(A) → begin(B) → complete(A) → complete(B)`, затем ещё одна успешная попытка: новый запуск очищает старый результат, старые id отвергаются, идентификаторы возрастают и не образуют простой двухэлементный цикл.
- `begin(A) → cancel → begin(B) → complete(A) → complete(B)`: запоздалый результат отменённой попытки не завершает новую.

После каждого существенного события проверяется состояние и результат, поэтому промежуточная порча не скрывается правильным итоговым состоянием. Имена тестов и `subTest` с id/результатом дают воспроизводимую диагностику. Два разных результата отделяют принятие текущего значения от сохранения предыдущего или чужого.

Восемь коротких сценариев покрывают различимые риски состояний idle/waiting/done/cancelled, две причины перезапуска и конкурирующие порядки cancel/complete. Третий успешный запуск добавлен только для повторного использования id. Перебор произвольных длин не нужен для этих конкретных ошибок: он повысил бы стоимость и затруднил диагностику без обоснованной новой границы. Это сценарная проверка, а не доказательство свойств на всех бесконечных трассах или гарантии прогресса при отсутствии ответа.
