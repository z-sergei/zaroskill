# Вердикт и границы

Тесты полезны, но есть конкретные недостающие различия. Прочитаны весь `cancellation.py`, весь `test_cancellation.py` и все четыре записи `mutation-report.json`; в самостоятельном проекте нет других потребителей или тестовых наборов. Ожидания основаны на контракте `task.md`. Production, тесты и приложенный отчёт сохранены без изменений.

**Отчёт — заранее предоставленная синтетическая фикстура.** Я не запускал мутационный инструмент и не выдаю её статусы за свои измерения. Отдельно выполнены обычный unittest и три узких ручных fault-probe в одноразовой копии. Их результаты не исправляют задним числом статусы фикстуры и не составляют общую оценку mutation score.

## Каждый элемент отчёта

### M1 — `SURVIVED`: эквивалентное преобразование

`paid_cents // 4` и `(paid_cents - paid_cents % 4) // 4` дают один результат на всём заявленном домене. Для неотрицательного целого `n = 4q + r`, где `0 <= r < 4`, оба выражения равны `q`. Python-целые не переполняются, а отрицательные значения отвергаются до этой ветки. В наблюдаемом контракте нет требования к числу арифметических операций.

**Действие:** считать M1 эквивалентным в рассматриваемом домене; не добавлять тест ради его «убийства» и не менять требования. Это математическое обоснование по коду, а не выполненная мутационная проверка. Запуск на остатках 0, 1, 2, 3 и очень большом целом мог бы служить иллюстрацией равенства, но конечная выборка слабее приведённого доказательства. M1 ничего не доказывает о достаточности проверки округления четверти: разные неэквивалентные ошибки округления остаются отдельным вопросом.

### M2 — `SURVIVED`: реальный пропуск границы

Сдвиг `>= 48` на `>= 47` неправомерно делает отмену за 47 часов бесплатной. Валидный контрпример: `(47, 100)`, требуется 25, получается 0. Существующие входы 48 и 72 этого не различают; оплата выбрана ненулевой и достаточно большой, чтобы комиссия не округлилась до 0.

**Действие:** рекомендовать тест `cancellation_fee(47, 100) == 25`, сохранив существующий случай 48 часов. Это разные стороны договорной границы. В исполняемый набор тест не добавлялся, как и предписано заданием.

**Подтверждено исполнением:** в копии с одной этой подменой все 6 неизменных тестов прошли; отдельный вызов вернул 0 вместо 25. Значит это здоровое выполнение неверного варианта и реальная слепая зона, а не ошибка запуска. Предложенный тест должен пройти на оригинале и упасть на M2; такой новый тест не исполнялся.

### M3 — `ERROR`: нет свидетельства из фикстуры; существующий тест чувствителен

Фикстура сообщает `tests_run: 0`, bootstrap упал с отсутствующим `mutation_worker_runtime` до обнаружения тестов. Этот ERROR нельзя считать ни обнаруженным дефектом, ни выжившим вариантом. Он ничего не говорит о качестве assertions.

Подмена меняет округление половины для нечётной оплаты. Уже существующий `test_half_fee_rounds_down` вызывает `(12, 101)` и требует 50; M3 возвращает 51.

**Действие:** не добавлять дублирующий тест; сохранить имеющийся. Для настоящего инструмента сначала нужно восстановить поддерживаемое окружение worker и затем повторить узкий запуск, наблюдая старт/число тестов и причину падения. Установка и ремонт инструмента здесь не выполнялись.

**Подтверждено отдельным исполнением:** ручная замена только указанной строки в копии дала 6 выполненных тестов и один assertion failure в `test_half_fee_rounds_down`: `51 != 50`, exit 1. Это реальная чувствительность именно этого теста, независимая от неудачного synthetic worker.

### M4 — `TIMEOUT`: тайм-аут запуска, не проверка поведения

Фикстура сообщает 0 тестов и отсутствие test-start event: превышено время handshake запуска worker. Это не свидетельство зависания `cancellation_fee`, не обнаружение бесконечного цикла и не доказательство недостаточного timeout тестов. Сама указанная подмена добавляет лишь другую границу к конечному расчёту.

`>= 25` вместо `>= 24` неправильно относит 24 часа к половинной комиссии. Уже существующий `test_at_day_boundary`: `(24, 100)` → 25, а M4 вернёт 50.

**Действие:** не добавлять такой же граничный пример. Для реального инструмента исследовать запуск worker и события тестов; повторить после устранения причины. Простое повышение timeout или запись этого исхода в «killed» не подтверждает защиту.

**Подтверждено отдельным исполнением:** та же узкая ручная подмена в копии, 6 выполненных тестов, один assertion failure `50 != 25` в `test_at_day_boundary`, exit 1. Этот результат отделён от TIMEOUT в фикстуре.

## Контракт, качество и приоритеты

Сейчас покрыты: комиссия половины на поздней отмене (`0, 100`), начало четвертной комиссии (`24, 100`), начало бесплатной (`48, 100`), обычная ранняя отмена (`72, 100`), округление половины (`12, 101`) и отрицательный каждый из двух аргументов. Важные значения буквально указаны, наблюдается реальный результат публичной функции и `ValueError`. Проверок приватной структуры и doubles нет.

| Свойство | Оценка |
| --- | --- |
| Regression protection | **mixed**: значимые правила защищены, но M2 действительно проходит; четвертная комиссия проверена только для делящейся на 4 оплаты |
| Refactor resistance | **strong по коду**: только поддерживаемая функция и её результат/исключение; отдельный refactor probe не выполнялся |
| Feedback and reliability | **strong локально**: детерминированные in-process проверки, без случайности и I/O; каждый запуск сообщал 6 тестов и около `0.000s`. CI, производительность и реальное окружение mutation worker — **unknown** |
| Maintainability | **strong**: короткие явные примеры, независимые ожидания; число тестов само по себе не служит оценкой |

Приоритетные рекомендации:

1. **Medium, executed:** добавить 47 часов / 100 центов → 25 для выявленной M2 ошибки. Место — рядом с `test_at_free_boundary`.
2. **Medium, demonstrated by code:** рядом с `test_at_day_boundary` добавить четвертное округление `(24, 103)` → 25. Сейчас единственный четвертной платёж 100 не отличает floor от округления вверх/до ближайшего целого; например `round(103 / 4)` дало бы 26, тогда как на 100 текущий тест прошёл бы. Это самостоятельный контрактный пробел, не попытка убить эквивалентный M1. Подмена и новый тест не исполнялись.
3. **Low, demonstrated by code:** дополнить нижнюю сторону перехода примером `(23, 100)` → 50. Все существующие входы ниже 24 — 0 и 12; ошибка `>= 23` осталась бы незамеченной. Это предложенная различительная проверка, не наблюдавшийся результат инструмента.

Объединять или удалять существующие тесты на основании этого маленького отчёта не предлагается: границы, обычные примеры и округление имеют разные обязанности. Не предлагается исчерпывающий перебор чисел или тест на каждый возможный мутант. Верхний предел не вводится; конечный набор примеров не доказывает поведение для всех целых. Отрицательные аргументы сохраняют отдельную проверку каждого аргумента.

## Реально выполненные проверки

Обычная команда в исходной папке: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -v`: 6 тестов, `OK`, exit 0 до и после probes; пропусков, expected failures и ошибок setup не было.

В `probes/05_cancellation` копировались исходник и неизменный тестовый файл. На каждую подмену восстанавливался оригинал, затем менялась одна строка. Тот же unittest:

- Контроль копии: 6 тестов, `OK`, exit 0.
- M2: 6 тестов, `OK`, exit 0; `python3 -c 'from cancellation import cancellation_fee; print(cancellation_fee(47, 100))'` вернул 0.
- M3: 6 тестов, один содержательный assertion failure, exit 1.
- M4: 6 тестов, один содержательный assertion failure, exit 1.

Полный вывод сохранён в `probes/05_cancellation/control.txt`, `M2_focused_probe.txt`, `M3_focused_probe.txt`, `M4_focused_probe.txt`. Затем исходник копии восстановлен, SHA-256 исходного production, тестов и JSON подтвердил их неизменность. M1 не запускался отдельно. Ни мутационный инструмент, ни автоматическая внешняя кампания не запускались. Рекомендованные новые тесты остаются рекомендациями.
