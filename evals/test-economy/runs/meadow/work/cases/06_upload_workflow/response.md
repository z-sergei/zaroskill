# Карточка временного контракта

Источник: task.md; все перечисленные свойства required, а не характеристика текущей реализации. Граница — настоящий UploadSession и последовательные публичные begin/complete/cancel; состояние и result наблюдаемы, active id устанавливается begin и возвращается вызывающему. Других производителей callback или I/O в проекте нет. Контракт допускает старые, чужие и повторные complete, поэтому эти вызовы достижимы без выдуманного состояния.

Safety: завершить можно только текущий id в waiting; отказ и исключение сохраняют состояние/результат и способность текущей попытки завершиться; после cancel/done позднее событие не меняет результат. Новый begin сбрасывает result и возвращает положительный целый id строго больше прошлого. Useful work: корректный complete действительно завершает попытку. Обязанности eventually complete нет: среда может не прислать callback; не добавляем тайм-аут или fairness.

Выбраны прямые короткие сценарии с checkpoint после каждого существенного события; отдельная модель, генератор и framework для четырёх фаз не нужны. Итоговая карта последовательностей и результаты приведены ниже.


## Выполненные изменения и различающие последовательности

Исходные полезные сценарии сохранены: обычный успех, отмена, чужой будущий id с последующим корректным завершением. Отмена расширена поздним callback и повторной отменой. Теперь восемь коротких независимых тестов, без новой модели, helpers, приватных полей или зависимостей. Ожидаемые True/False проверяются именно как булевы результаты. Тип id, положительность и строгий рост проверяются без требования начинать с 1 или увеличиваться ровно на 1.

| Тест / достижимая история | Существенные checkpoints и различаемый риск |
| --- | --- |
| test_successful_upload: idle → begin A → complete A | idle/None, положительный целый A, waiting/None, True и done/report.csv; защищает полезное завершение, а не только отказы |
| test_cancelled_upload_rejects_late_completion_and_repeated_cancel: begin A → cancel → complete A → cancel | первая отмена True и cancelled/None; позднее завершение False и всё ещё cancelled/None; повторная отмена False, состояние неизменно |
| test_unknown_completion_preserves_current_attempt: begin A → complete A+1 → complete A | чужой id False и waiting/None; исходный A затем успешно завершает загрузку; отказ не теряет активную попытку |
| test_idle_session_ignores_completion_and_cancel: idle → complete 1 → cancel → begin → complete | оба события в idle False и idle/None; затем настоящий старт и успех остаются возможны |
| test_rejected_begin_keeps_the_current_attempt_finishable: begin A → begin (RuntimeError) → complete A | сразу после исключения waiting/None; затем True и done/original.csv; одна проверка публичного state без последующего complete не поймала бы порчу скрытого активного id |
| test_completed_upload_preserves_result_after_duplicate_and_cancel: begin A → complete A(first) → complete A(duplicate) → cancel | первый результат сохраняется после каждого отклонённого события; попытка done не становится cancelled и не переписывает результат |
| test_restart_after_success_clears_result_and_rejects_old_attempt: begin A → complete A(first) → begin B → complete A(obsolete) → complete B(second) | B целый и > A; сразу waiting/None, хотя раньше был непустой result; старое A не принимается и не мешает завершить B |
| test_restart_after_cancel_ignores_old_result_before_and_after_success: begin A → cancel → begin B → complete A(old-before) → complete B(current) → complete A(old-after) | B > A, waiting/None; до успеха B старое A не меняет waiting и активную попытку; после успеха B старое A не меняет done/current.csv |

Разные строки-результаты делают перепутанные события видимыми. После запретных событий assertions выполняются немедленно: поздний правильный complete не может скрыть уже ошибочное изменение. Повторный start после done нужен отдельно от restart после cancelled: только первый начинает с непустого результата и обнаруживает забытый сброс. Старое A проверяется и до текущего завершения B, и после; это разные проверки авторитетности id и терминальности результата. Ошибочный повторный begin исследован отдельно от корректного restart — контракт требует исключение и сохранение действующей попытки.

Выбранного набора достаточно для перечисленных различий: принятие старого id, потеря активного id при отказе, переписывание готового результата, разрешение позднего callback после отмены, запрет допустимого restart, повторное использование id и забытый сброс результата. Это конечные сценарии, не доказательство произвольных историй или всех значений id. Нет требований сети, потокобезопасности, автоматического завершения или внешней доставки — они не заявлены как проверенные. Bounded exploration и formal proof не выполнялись; общая модель и TLA+ для этих локальных рисков увеличили бы поддержку без дополнительной нужной границы наблюдения.

## Реальная проверка

Все тестовые команды: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -v`; полный вывод в execution.md.

1. Исходная папка и контрольная копия: по 3 теста OK.
2. В probes/06_upload_workflow сравнение id в complete заменено с `!=` на `>`: будущий чужой id всё ещё отвергается, но старый id ошибочно принимается. Исходные 3 сценария действительно прошли. После копирования нового test_upload.py два restart-сценария дали assertion `True is not False` на старом callback. Это **scenario reproduced**, не ошибка сборки и не нулевая discovery.
3. На восстановленной копии 8 тестов OK. Во второй точечной порче отклоняемый begin менял активный id перед RuntimeError. Новый тест rejected_begin дошёл до последующего complete и упал на `False is not True`; остальные 7 прошли. Это подтверждает необходимость проверки продолжения после отказа.
4. Отдельная допустимая вариация генерации id с шагом 2 прошла все 8 тестов. Контракт требует строгое возрастание, а не последовательные числа; это проверенная устойчивость к одной допустимой внутренней замене, не утверждение о любых refactor.
5. Все probes восстановлены. Финально копия и исходная папка: по 8 тестов OK. Production upload.py побайтово неизменён; его хеш записан в execution.md.

Результат: scoped verification выполнена, заявленные сценарии исполнены. Неисполненных обязательных шагов нет. Применён локальный state-machine-verification/SKILL.md и references/temporal-checks.md, sources.md; процессы других навыков сюда не добавлялись.
