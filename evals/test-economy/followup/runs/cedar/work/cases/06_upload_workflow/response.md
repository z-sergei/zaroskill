# Проверка жизненного цикла загрузки

Требуемые свойства взяты из `task.md`; граница — настоящий `UploadSession`, его методы, `state` и `result`. События вызываются последовательно. Активная попытка проверяется через возможность завершить её после отклонённого события, без доступа к закрытым полям. Обязательство полезного результата: корректное завершение текущей попытки немедленно даёт `done` и переданное значение. Время, доставка callback, I/O, потоки и безусловное eventual completion вне контракта.

План и выбранные последовательности:

| Свойство | Различающая последовательность | Проверка |
| --- | --- | --- |
| До старта нет принимающего владельца | complete → cancel из idle | `test_events_before_begin_preserve_idle` |
| Второй begin не теряет текущую попытку | begin A → отвергнутый begin → complete A | `test_rejected_begin_preserves_the_active_attempt` |
| Завершение раньше отмены фиксирует результат | begin A → complete A → повтор/чужой complete → cancel | `test_completed_result_survives_repeated_completion_and_cancel` |
| Отмена раньше завершения запрещает поздний результат | begin A → cancel → complete A → cancel | `test_cancelled_attempt_ignores_late_completion_and_repeated_cancel` |
| Перезапуск после done и cancelled отделяет поколения | закончить A → begin B → complete A → complete B → complete A → begin C → complete A/B → complete C | `test_restarts_keep_old_results_out_of_new_attempts`, две начальные развилки |
| Прежние позитивные сценарии и чужой id во время ожидания | Существующие три теста | Сохранены |

Исходный набор выполнен: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -v`, 3 теста, OK. Усиленный набор той же командой: 8 тестов, OK, exit 0. После одноразовых проверок повторён итоговый запуск: 8/8, exit 0. Production изначально соответствует контракту; это усиление проверок, а не TDD исправления.

Состояние и результат проверяются после каждого значимого события, поэтому последующее правильное завершение не скроет временное применение устаревшего результата. Разные строки различают прежний, новый и запрещённый результаты. Успешное завершение действующей попытки после отклонения чужого/старого id или повторного begin обнаруживает скрытую потерю активной попытки. Два порядка `complete → cancel` и `cancel → complete` имеют разные ожидаемые конечные состояния. Старые результаты проверяются и до нового успеха, и после него. Три поколения обнаруживают повторное использование id после первого перезапуска и различают ближайшую и более старую попытки. Проверяется строгий рост, без требования шага +1 или начального id 1.

Эти короткие истории различают известные риски потери владельца, принятия позднего результата, повторной записи результата и неверного сброса при перезапуске. Это сценарная проверка, не полный перебор всех историй и не доказательство неограниченного временного свойства. Восемь обычных `unittest`-методов и две развилки одного сценария сохраняют дешёвый запуск без нового фреймворка, моков или копии модели. `subTest` указывает исходный исход и id; имена тестов указывают нарушенный контракт. Соседние простые тесты оставлены: они дают короткую диагностику локального перехода, а более длинные истории проверяют отдельные временные обязательства, даже если иногда ловят те же ошибки.

В `probes/` выполнена адресная проверка чувствительности неизменённых утверждений на копиях текущего случая:

- потеря активной попытки при отвергнутом begin → FAIL: действующее завершение вернуло False;
- принятие позднего завершения после отмены → FAIL: ожидался False;
- повторное использование id после done → FAIL: `1 not greater than 1` / `2 not greater than 2`;
- возвращение False с перезаписью результата повторного завершения → FAIL: `replacement.csv` вместо `original.csv`;
- сохранение прежнего результата при begin → FAIL: непустой результат в waiting.

Все пять дефектов дали именно assertion failures, без ошибок импорта или запуска. Допустимое изменение шага id с +1 на +7 сохранило 8/8 зелёных тестов. Команда: `PYTHONDONTWRITEBYTECODE=1 python3 probes/upload_sensitivity.py` из корня cedar; exit 0. Полные команды и выводы сохранены в `probes/results.json` и отдельных `output.txt`; это ограниченные эксперименты, не оценка полноты мутационного покрытия.

`upload.py` не менялся: SHA-256 до и после — `2eb255004f3ff1076292c96bc960c8abcee553e989f3605de4e8bb101c77b725`. Приватные поля production в тестах не используются. Блокирующих неопределённостей в заданной границе нет.
