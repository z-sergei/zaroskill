# Результат проверки временных свойств

Обязательные свойства взяты из `task.md`, не из веток реализации. Граница — реальный `UploadSession` через `begin`, `complete`, `cancel`, `state`, `result`. События последовательны; I/O, потоки, время и доставка callback вне границы. Активную попытку наблюдаем косвенно: после отвергнутого события именно прежний id должен успешно завершиться.

Safety: поздние/чужие/повторные завершения и отмена вне ожидания не меняют наблюдаемый результат; ошибочный `begin` не заменяет попытку. Каждая успешная новая попытка получает больший целочисленный id и очищает результат. Полезный исход проверяется явно: активное завершение принимается и публикует заданную строку. Ожидание без завершающего события допустимо; утверждений об eventual completion нет.

Три соседних теста сохранены. Добавлены пять сценариев; проверки идут после каждого существенного события, поэтому временно испорченный результат нельзя скрыть последующим правильным завершением. Существующий успешный сценарий дополнительно проверяет целочисленный id.

| Порядок событий | Что он различает |
| --- | --- |
| В `idle`: чужие завершения → отмена → нормальная загрузка | Отказы не создают результат и не мешают следующей попытке; проверены id -1, 0 и 1 |
| `begin A → begin с ошибкой → complete A` | Ошибка повторного запуска не должна незаметно заменить активную попытку; одного `RuntimeError` недостаточно |
| `begin A → complete A → duplicate A → cancel → foreign complete` | Первый результат сохраняется после повторного ответа, поздней отмены и чужого ответа |
| `begin A → cancel → complete A → cancel → foreign complete` | При обратном порядке отмена побеждает; позднее завершение не восстанавливает отменённую загрузку |
| `A done/cancelled → begin B → late A → complete B` | Перезапуск разрешён из обоих терминальных состояний, очищает результат и получает больший id; устаревший ответ не завершает B и не лишает её права завершиться |
| Затем `begin C → late A → late B → complete C` | Три последовательных id возрастают; отвергаются и ближайшая, и более ранняя попытки, а C сохраняет активность |
| Сохранённый `begin A → foreign complete → complete A` | Чужой ответ без перезапуска не заменяет активную попытку |

Эти последовательности покрывают разные риски: порядок отмены/завершения, повтор события, чужая и устаревшая идентичность, новый запуск после обоих исходов, потеря активной попытки при отказе. Для них достаточно двух исходов первой попытки, трёх последовательных попыток и различающихся строк результатов. Это выбранные конечные сценарии, не перебор всех историй, не формальное доказательство и не проверка прогресса во времени.

Цена поддержки — пять новых методов, один из них с двумя понятными `subTest` по исходу предыдущей попытки. Нет копии автомата как oracle, приватных полей, фиксации точных значений id, зависимостей или общего фреймворка. Пересечение с тремя исходными тестами полезно: их короткие сценарии отдельно диагностируют базовый успех, отмену и чужое завершение.

Фактически выполнено:

- `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -v` до изменений — 3 теста, OK; после изменения и повторно после проб — 8 тестов, OK.
- `PYTHONDONTWRITEBYTECODE=1 python3 probes/upload_fault_probes.py` из общего разрешённого корня — три отдельные копии. В каждой прежние три теста прошли, а новый целевой сценарий упал с содержательным `AssertionError`: заменён активный id перед `RuntimeError`; принят ответ предыдущей попытки; поздняя отмена стёрла готовый результат. Это проверка чувствительности новых тестов, а не найденные дефекты рабочего production.
- Рабочий `upload.py` остался побайтно неизменным; исходный и итоговый SHA-256 совпадают. Результаты и команды проб сохранены в `probes/upload_probe_results.json`, подробные ошибки — в `probes/*/distinguishing.txt`, общий журнал — в `execution.md`.

Все проверки выполнены через Python stdlib. Production и публичный API не менялись.
